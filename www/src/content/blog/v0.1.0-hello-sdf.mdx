I've been working with stacked pull requests for years. If you've ever broken a large feature into a chain of small, focused PRs — each one building on the last — you know how good the workflow *feels*. Reviewers get digestible diffs. CI runs against coherent slices. You can land parts of a feature independently.

But you also know the other side: keeping the stack in sync is a constant, manual grind.

## The overhead nobody talks about

Every team that adopts stacked PRs eventually hits the same wall. It's not the stacking itself — it's everything that happens *after*.

Your first PR in the stack gets approved and merged. Now you need to rebase the second branch onto `main`, then rebase the third onto the second. Update the base branch settings on GitHub for each downstream PR. Check that the PR descriptions still make sense — the "depends on #42" link now points to a merged PR, the stack navigation table is wrong, the context you wrote for reviewers is stale.

And if any of those rebases produce a conflict? Now you're resolving merge conflicts across multiple branches, one at a time, hoping you don't introduce regressions in a layer that was already reviewed.

Over the years I've patched this with git aliases, small bash scripts, bits of automation here and there. Each one solved a piece of the puzzle — but never the whole thing. The overhead always crept back.

## SDF: the whole picture

SDF is the tool I kept wanting to exist. It understands the full lifecycle of a PR stack — not just the rebasing, but the descriptions, the base branches, the navigation links between PRs, and the merge strategy.

The commands map to how you already think about stacked work:

- **`sdf init`** and **`sdf branch`** — create a stack and add branches to it
- **`sdf status`** — see where every branch and PR stands at a glance
- **`sdf pr`** — open GitHub PRs with correct bases and stack navigation injected into descriptions
- **`sdf sync`** — the core: after an upstream PR merges, cascade-rebase every downstream branch, update PR bases, and refresh descriptions — all in one command
- **`sdf merge`** — squash-merge the head PR and cascade-rebase the rest of the stack
- **`sdf fetch`** — discover existing PR stacks from GitHub and rebuild local state

The key insight is that `sdf sync` and `sdf pr` don't just move branches around — they keep PR descriptions and metadata in sync too. Before you ask for a review, before you hit merge, the stack navigation and context are already accurate. That's the overhead that scripts and aliases never fully solved.

## AI-powered conflict resolution

Rebases will sometimes produce conflicts — that's unavoidable. What's new is how SDF can handle them.

With opt-in Claude integration, SDF resolves rebase conflicts semantically. Instead of dumping conflict markers for you to sort out manually, it reads the surrounding context, understands the intent of both sides, and produces a resolution. You review the result and move on.

This is especially useful deep in a stack, where conflicts are often mechanical (an import changed upstream, a function signature shifted) but tedious to resolve by hand across multiple branches.

## Get started in 30 seconds

```bash
brew install pavelpascari/tap/sdf
sdf doctor          # verify git, gh, and optional Claude CLI
sdf init --branch db-schema my-feature
```

Read the full [Getting Started guide](/docs/getting-started) for a complete walkthrough.

## What's next

This is v0.1.0 — the foundation. The core workflow is solid, and I'm using it daily. The plan from here is to keep iterating and make the tool more resilient: better edge-case handling, smoother recovery when things go sideways, and tighter integration with the tools you already use.

If stacked PRs are part of your workflow, I'd love for you to give SDF a try. Feedback, bug reports, and contributions are all welcome on the [GitHub repo](https://github.com/pavelpascari/sdf).
