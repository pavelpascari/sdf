There's a class of bug that only appears when you squint at commit graphs long enough. The tool runs, prints green checkmarks, pushes branches &mdash; and three syncs later you notice that `git log main..your-branch` shows five commits where there should be four. One of them is a ghost: a commit from a parent branch that has no business being there.

This post is about finding and fixing that exact bug in SDF's `sdf sync` cascade rebase. It's a story about `git rebase --onto`, the difference between two SHAs that _look_ like they should be the same, and why a fast-path optimization needs to be very careful about which question it asks.

## The setup: how cascade rebase works

SDF manages stacked PRs &mdash; chains of dependent branches where each one builds on the previous. A three-branch stack looks like this:

```
main (M1) → branchA [a1] → branchB [b1] → branchC [c1]
```

Each node in the stack stores a `BaseTip` &mdash; the SHA of the parent branch's tip at the time of the last sync. When `sdf sync` runs, it walks the chain and checks whether each branch's `BaseTip` still matches its parent's current tip. If not, it rebases.

The rebase command is the three-argument form:

```bash
git rebase --onto <new-parent> <old-base> <branch>
```

This tells Git: "take the commits between `<old-base>` and `<branch>`, and replay them onto `<new-parent>`." The `<old-base>` is the boundary &mdash; it defines which commits belong to the branch versus which belong to the parent. Get it wrong, and you either lose commits or include ones that shouldn't be there.

## The bug: two SHAs walk into a bar

SDF has a feature where `sdf sync` (without the `--full` flag) intentionally skips rebasing when `main` advances from unrelated work. The idea is: if someone merged a totally unrelated PR into `main`, you don't want to rebase your entire stack just because the base moved. You want to keep working and only rebase when you choose to (via `sdf sync --full`).

To implement this, the sync loop tracks two different values for the base branch:

- **`preFFBaseTip`** &mdash; the local `main` tip _before_ fast-forwarding to the remote
- **`currentParentTip`** &mdash; the actual current tip of `main` _after_ fast-forward

The `compareTip` variable controls whether a branch "looks stale":

```go
compareTip := currentParentTip
if !opts.fromHead && parent == s.Base && opts.preFFBaseTip != "" {
    compareTip = opts.preFFBaseTip  // use the old tip for comparison
}
```

When `compareTip != node.BaseTip`, something changed. The next question is: does the branch need a real rebase, or can we just update the bookkeeping?

There's a fast path for the second case &mdash; the "update-tip" path. If the parent's tip is already an ancestor of the branch (meaning the branch already includes those changes), no rebase is needed. Just update `BaseTip` and move on.

Here's where the bug lived:

```go
if compareTip != node.BaseTip {
    if gitpkg.IsAncestor(compareTip, node.Branch) {  // ← THE BUG
        node.BaseTip = currentParentTip               // ← stores THIS
        continue  // skip rebase
    }
    // ... actual rebase ...
}
```

Spot it? The `IsAncestor` check uses `compareTip` (which might be `preFFBaseTip` &mdash; the _old_ base), but then stores `currentParentTip` (the _new_ base) as `BaseTip`.

When those two values differ, the code is asking: "is the _old_ base an ancestor of this branch?" &mdash; and if yes, recording: "the branch is based on the _new_ base." But the new base might not be an ancestor at all. The branch was never rebased onto it.

## The corruption cascade

Here's the concrete scenario that breaks things:

**Setup:** `main@M1 → branchA[a1]`. `BaseTip = M1`.

1. `main` advances to `M2`. Someone manually rebases `branchA` onto `M2` (outside SDF).
2. `main` advances further to `M3`.
3. `sdf sync` (without `--full`) runs:
   - `preFFBaseTip = M2` (local main before fast-forward)
   - `currentParentTip = M3` (main after fast-forward)
   - `compareTip = M2` (using pre-FF value since `parent == main`)
   - `M2 != M1` (BaseTip) → something changed
   - `IsAncestor(M2, branchA)` → **true** (branchA was rebased onto M2)
   - `node.BaseTip = M3` ← **but M3 is NOT an ancestor of branchA!**

`BaseTip` is now lying. It claims the branch is based on `M3`, but the branch has never seen `M3`.

On the _next_ sync, when a downstream branch needs rebasing:

```bash
git rebase --onto branchA <corrupted-BaseTip> branchB
```

The `<corrupted-BaseTip>` doesn't properly identify the boundary between branchA's commits and branchB's commits. The result: commits from branchA's old rebase get included in branchB's history. Ghost commits.

## The fix: ask the right question

The fix is one-line-per-call-site simple:

```go
// Before (buggy):
if gitpkg.IsAncestor(compareTip, node.Branch) {

// After (fixed):
if gitpkg.IsAncestor(currentParentTip, node.Branch) {
```

The `compareTip` variable should only control whether to _enter_ the check ("has anything changed?"). The ancestor verification must always use the _actual_ current parent tip &mdash; because that's the value we're about to store. If `currentParentTip` isn't an ancestor of the branch, the branch needs a real rebase, period.

This change was needed in three places: the execution loop (`runSyncFrom`), the plan computation (`computeSyncPlan`), and the "has real work" pre-scan.

## Defense in depth: the `rebased` map

While tracing through the code, we noticed another asymmetry. The plan computation (`computeSyncPlan`) maintains a `rebased` map &mdash; when a branch is rebased, its children are force-checked regardless of SHA comparison:

```go
rebased := make(map[string]bool)
// ...
needsRebase := rebased[parent]  // force cascade if parent was rebased
```

The execution loop (`runSyncFrom`) had no such map. It relied entirely on SHA comparison for cascade propagation: after rebasing branchA, branchA's tip changes, so branchB's `BaseTip` differs from `currentParentTip`, triggering branchB's rebase.

This works in practice &mdash; a rebase always produces a new SHA. But it's fragile by design. The plan says one thing; the execution relies on a different mechanism. We added a matching `rebased` map to the execution loop:

```go
forceCascade := rebased[parent]
if forceCascade || (node.BaseTip != "" && compareTip != node.BaseTip) {
    if !forceCascade && gitpkg.IsAncestor(currentParentTip, node.Branch) {
        // update-tip fast path — only when NOT force-cascading
        // ...
    }
    // rebase path...
}
```

And wired it through the `--continue` path, so that after manual conflict resolution, downstream branches know their parent was just rebased:

```go
return runSyncFrom(root, s, progress.ResumeIndex+1, nil, result, bus,
    map[string]bool{progress.PausedAt: true})
```

## The git internals angle

If you've ever wondered why `git rebase --onto` has three arguments instead of two, this bug is a good illustration. The three-argument form:

```bash
git rebase --onto <newbase> <upstream> <branch>
```

is really answering: "which commits are _mine_?" The range `<upstream>..<branch>` defines the commits to replay. Everything in that range gets cherry-picked onto `<newbase>`. Everything outside it stays behind.

When `<upstream>` is wrong &mdash; pointing to a commit that's not actually in the branch's ancestry, or pointing too far back &mdash; Git falls back to `merge-base` heuristics. Sometimes it works. Sometimes it includes commits from a sibling rebase (same original commit, different base), producing the "phantom commit" symptom.

In our case, the corrupted `BaseTip` was a _sibling_ SHA: a different rebase of the same original commit onto a different base. SHAs `d93407b` and `7954b4c` are both "branchA rebased onto main" &mdash; just onto different versions of main. Neither is an ancestor of the other. Using the wrong one as `<upstream>` breaks the boundary.

## What we tested

The existing test suite only covered `computeSyncPlan` (the dry-run planner). The execution path (`runSyncFrom`) had zero test coverage. We added six tests:

| Test | What it proves |
|------|---------------|
| `UpdateTipAncestorCheck` | Plan shows "rebase" (not "update-tip") when only `preFFBaseTip` is ancestor |
| `UpdateTipNoFalseCorruption` | `BaseTip` is always a valid ancestor after sync |
| `CascadePropagation` | Full cascade through 3-branch stack, correct commit counts |
| `ForceCascadeFromRebasedParent` | All branches rebased, verified via `SyncResult` |
| `CascadesDownstream` | `--continue` cascades to downstream branches |
| `WarnOnMergeBaseFallback` | Warning emitted when `BaseTip` is corrupted |

The first two are the ones that caught the bug &mdash; they failed before the fix and passed after. The rest are characterization tests that document the correct cascade behavior.

## Takeaways

**Fast paths need to validate what they store, not just what they check.** The bug was a mismatch between the condition variable (`compareTip`) and the stored value (`currentParentTip`). The fast path asked "is X an ancestor?" but recorded "Y is the base." When X ≠ Y, corruption follows.

**Plan and execution should use the same cascade mechanism.** Having `computeSyncPlan` use a `rebased` map while `runSyncFrom` relied on SHA comparison meant the plan could say "rebase needed" while execution might disagree. They should converge.

**Test the execution path, not just the planner.** It's tempting to only test the function that computes the plan &mdash; it's pure, deterministic, easy to assert on. But the bugs live in the loop that actually calls `git rebase --onto`, handles conflicts, updates state, and pushes. That's where the SHAs interact with real Git.

The fix is in [PR #214](https://github.com/pavelpascari/sdf/pull/214). Two files changed, three call sites fixed, one map added. The kind of bug that takes longer to understand than to fix.
